# Implementation Plans

Generated by the improve skill on 2026-08-26, against commit `57c60b6`.

These twenty-one plans cover every actionable finding from the audit, plus one
requested feature (021). Execute in the order below unless dependencies say
otherwise. Each executor: read the plan fully, run its drift check first, honour
its STOP conditions, and update your row when done.

**Three standing rules for every plan here.** None is optional:

1. **Never run `scripts/dependencies.sh --install` or `scripts/setup_firewall.sh`
   directly.** The first invokes `sudo pacman` and a multi-hundred-crate `cargo`
   build; the second edits this machine's live firewall. All verification of
   those scripts goes through stubbed test harnesses that put fake binaries on
   `PATH`.
2. **Never edit anything under `/usr/share/omarchy/`.** That is the packaged
   Omarchy shell, not this repository, and changes there are overwritten on the
   next system update.
3. **Never modify `backend/`.** It is byte-identical to upstream
   (`git log 3f54d18..HEAD -- backend/` is empty), which is what keeps rebases
   cheap and what plan 015's release model depends on. Backend bugs go upstream
   via plan 018.

## Two plans are blocked on a decision only the maintainer can make

**Plan 015** asks: *does this fork publish its own helper releases, or
permanently consume upstream's?* It implements the second (Option A) because
`backend/` has never been touched — but the first is a legitimate choice, and
plan 016 depends on which is picked. Do not execute 015 until this is confirmed.

**Plan 006** asks: *should the firewall rules be scoped to the local network by
default, or left global with an honest banner?* It implements the second, with
`--local` as opt-in, because a plugin that silently stops working after a network
change is a worse failure than a documented open port. Both are defensible.

Plan 020 exists to settle a third, larger question — whether Quick Share should
live in the Rust helper at all — which is currently being decided by inertia.

## What the audit found, and where it went

The audit produced 25 vetted findings across correctness, security, tests, docs,
dependencies and direction. Every one that is actionable is planned above.

The five Rust findings became plan 018 rather than code changes: `backend/` is
byte-identical to upstream, so patching locally would fork it and pay rebase cost
forever, for bugs that affect every upstream user equally. Two of the five are
things users hit routinely — sending a file whose name contains `shipping`
reports "PIN required", and a discovery round that finds nothing leaves the panel
saying "Finding devices…" forever.

The three direction findings became plans 019 (spike) and 020 (ADR). Clipboard
text over Quick Share is folded into 019, because it is gated on the same
upstream conversation.

## Implementation notes from the first executed work

**021 was implemented directly, ahead of its stated dependencies**, folding in the
parts of 007 and 008 it needed:

- 007 is fully done: `modeIn` and `quickShareIconFor` are exported, alongside the
  new name functions.
- 008 is **partially** done. `Model.displayName` exists and `upsertDevice` uses

- The rename-restart trap 021 predicted was real: `finishReceiverShutdown` calls

  verified to fail without it.

## Findings considered and rejected

Recorded so nobody re-audits them:

- **`base-devel` is a pacman group that prompts for member selection** — false.
  It has been a meta-package since 2022; verified with `pacman -Qi base-devel` on
  the target machine. No interactive prompt, nothing to fix.
- **The `t1nk33r` / `t1nk333r` spelling mismatch is typosquat-shaped** —
  downgraded to cosmetic. `t1nk333r` was confirmed via `gh` to be the real
  account, so the URL in `Panel.qml` is correct; only the plugin id reads
  differently. Renaming the id resets stored widget settings, so it is worth
  doing only as part of a deliberate rename.
- **Rewrite the `"oma.nearby"` literals in `tests/model.test.js`** — not worth
  doing. Every one is an *argument* to `barEntry` / `manifestVersion`, which take
  `pluginId` as a parameter. The tests are correctly parameterised and pass any
  string; the literals are cosmetically stale and functionally fine.
- **Promote `QuickShare.port` to a user setting** — not worth doing. It is
  deliberately pinned to match `setup_firewall.sh`'s `QUICKSHARE_PORT`; making it
  configurable would let the setting drift from the firewall rule with no
  mechanical link between them.
- **Abstract the duplicated launch-failure boilerplate across the three
  `Process` blocks** — below the threshold where an abstraction pays. Three sites
  with genuinely different recovery messages.

## Known remaining gaps, not planned

- **`ROBUSTNESS.md` has no Quick Share manual-test matrix.** Writing one honestly
  requires a real phone and real transfers, and `AGENTS.md` forbids claiming
  device paths were tested when they were not. Worth doing with hardware in hand.
- **No Quick Share transfer has ever been verified end to end.** Discovery is
  proven — a phone appears in the pane over BLE/mDNS — but the send path has not
  been exercised against a real device.
- **File paths containing newlines** break the chooser on both panes, which split
  its output on `\n`. Low impact, noted in plan 014's maintenance notes.
- **Release artifacts are unsigned.** SHA256 verification proves transport
  integrity only, since whoever publishes the binary publishes the checksum. The
  honest minimum is documenting the limitation; signing is a larger operational
  commitment.
